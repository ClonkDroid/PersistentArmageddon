# Codex task: deterministic Rust simulation foundation

## Objective

Build the first production-grade foundation for **Persistent Armageddon**: a deterministic, headless Rust simulation in which millions of soldiers remain individually addressable while distant activity is processed sparsely. This pull request establishes simulation truth, replay safety, logistics invariants, performance evidence, and interfaces for later tactical rendering.

The target population is **2,410,000 persistent soldiers**. A soldier must have one stable entity ID and one authoritative state. Rendering, snapshots, and level-of-detail changes must never create duplicate simulation entities.

## Workspace

Create a Cargo workspace with these initial crates:

- `sim-core`: dependency-light deterministic simulation library.
- `sim-server`: headless executable with a health/status endpoint and snapshot/command boundary suitable for a future browser client.
- `sim-wasm`: a minimal adapter that compiles for `wasm32-unknown-unknown` when that target is installed. Native workspace tests remain mandatory.

Keep frontend graphics out of this pull request.

## Required model

Implement and document:

- A monotonic `u64` world clock measured in simulation seconds.
- Stable generational entity IDs or an equivalently safe allocator.
- Data-oriented storage (prefer structure-of-arrays or dense component tables).
- Deterministic seeded random streams. Results may not depend on hash-map iteration order, wall-clock timing, thread scheduling, or machine-local entropy.
- Individually queryable soldiers with faction, position/cell, squad, role/rank, health, fatigue, hunger, thirst, sleep debt, carried ammunition, and inventory.
- Explicit squads and officers as simulation relationships, not labels generated by the UI.
- Logistics stocks and supply-vehicle transfers with conservation: supplies and ammunition may only move, be consumed, be produced by an explicit source event, or be destroyed by an explicit loss event.
- Sparse/event-driven needs processing. Do not scan 2.41 million entities every rendered frame or every simulated second. Store rates and last-materialized times and use a deterministic timing wheel, event queue, region scheduler, or documented equivalent.
- A hot tactical-cell path that can later run fixed-step combat at higher fidelity while cold regions remain deterministic and analytically updated.
- Versioned snapshots and a compact state digest for deterministic replay verification.
- Clear command/event boundaries so a server, WASM client, replay tool, or future renderer all consume the same authoritative state.

Use integers or fixed-point values for authoritative quantities where floating-point drift could break replay.

## Tests and invariants

Add automated tests covering at least:

1. no duplicate live entity IDs across spawn/despawn/reuse;
2. identical seed plus identical commands produces identical state digests;
3. snapshot save/load resumes to the same digest;
4. ammunition and supply conservation across successful and failed transfers;
5. needs materialization matches elapsed simulation time;
6. squad/officer references cannot point to dead or nonexistent entities after cleanup;
7. cold-to-hot-to-cold region transitions do not duplicate or lose soldiers.

Run and report:

- `cargo fmt --all -- --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`

## Performance proof

Add a reproducible release-mode benchmark or executable scenario that:

- initializes 2,410,000 individual soldier records;
- advances at least 60 simulated seconds with needs and scheduled logistics enabled;
- reports initialization time, advance time, throughput, and approximate resident memory;
- records the Codex environment's CPU/RAM/toolchain details;
- distinguishes measured results from the design goal of sustaining at least one simulated second per wall-clock second.

Do not claim the real-time goal is met unless measurements show it. If the environment cannot complete the full target, keep a smaller CI-sized test, preserve the full benchmark command, report the exact blocker, and propose the next optimization based on profiling evidence.

## Documentation and scope

Update the README with architecture, commands, benchmark results, and known limitations. Include an ADR explaining deterministic state ownership and simulation level-of-detail.

This is a foundation, not a claim of complete warfare fidelity. Do not add copyrighted game assets, copied lore text, orbital/psyker effects, graphics, networking prediction, or detailed combat ballistics in this pull request. Those should become later milestones on top of a verified core.
